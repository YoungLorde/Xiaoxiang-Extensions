# Xiaoxiang Config Extension — 2.1.3.2-patch

A patch to **2.1.3.2**, not a new version. Same mod, same version number, one
file you can drop in over the top. Everything below is a fix; nothing in it
changes a setting you have already chosen.

---

## 🔓 Realm Gate can be turned off again

Reported by **Strangesword69**, who had to uninstall this mod to play with Realm
Gate off. Thank you — that is exactly the report that gets something fixed. 🙏

**What was happening.** Realm Gate is a per-player setting, so the base mod asks
for your character before it answers anything about it. Before a world exists
there is no character, and its three answers are each reasonable alone and
useless together:

| | before a world exists |
|---|---|
| is the switch usable? | **no** — so it draws greyed out |
| is it on? | **yes**, always, whatever you chose |
| you clicked it | **nothing happens** |

A switch that is on, says it is on, and cannot be turned off. Searching the
config files for it finds nothing either, because it does not live in one — it
lives on your character. From where you are standing, the mod is forcing it on.

**What is fixed.** This mod now answers those three questions before a world
exists, so the switch on the origin screen is usable, shows what you actually
chose, and stays that way when the screen redraws.

**And it is in this mod's config screen now**, under **UI → Preferences**, named
**Realm Gate** — searchable by that name, and by "realm gate", "spell", "locked"
or "stuck". It is live in both directions: change it there and your character
changes to match; toggle it on the base mod's own screen and this follows.

> Realm Gate ON means a spell book you have not reached the realm for cannot be
> learned yet. OFF skips **only** that spell-book check — every other learning
> prerequisite still applies, exactly as the base mod describes. The base mod's
> own value is ON.

### 🩹 Why it broke, and why it will not break the same way again

The previous fix hooked the button's own click handler by its compiled name —
`lambda$init$4`, the fourth lambda in that screen's setup. **Lambda names are
generated by the compiler and numbered in source order, so they are not an
API.** Add a button anywhere earlier on that screen and lambda 4 becomes a
different handler entirely.

Worse, it was registered as optional, so when that happened it would not fail,
or warn, or write a line to any log. It would quietly stop applying.

It also could only ever fix the **click**. The label is rebuilt from the base
mod's own "is it on?" answer, which still said yes — so the screen went back to
reading ON the next time it drew itself.

The fix now hooks the three **named, public** methods behind the switch instead.
Those do not move when a screen is rearranged, because they are not part of one.
Fixing the question rather than the button means the label, the hint and the
click all agree, every frame, with nothing special-cased.

### 🔎 And there is a second cause, found in the new server version

Base mod **0.1.1532** — the server update — adds a hard lock this mod had never
seen:

```
realmLearningRestrictionsForceEnabled = false
```

in `config/xiaoxiang_cultivation-common.toml`, described by the base mod itself
as *"Force realm learning restrictions on (server hard lock)"* and *"enforced on
the server side; client-side config changes or modified clients cannot bypass
it."* It ships **off**. When a server turns it on, Realm Gate stays on for
everybody and nothing any client does will move it — which looks identical to a
mod forcing it.

**If your Realm Gate will not turn off, check that line first.**

This mod now reads the lock and gets out of its way: when the server has locked
Realm Gate, the setting shows what is actually true, stops trying to change it,
and writes one line to the log saying why. Fighting a server lock would give you
a switch that flickers and snaps back, which is worse than one that plainly will
not move.

The lock is read by name rather than called directly, so this still runs on base
mod versions older than 0.1.1532 — where there is no lock, and nothing to read.

## 👻 A companion mod's settings could go invisible

If you run a companion mod alongside this one, some of its settings may never
have appeared on screen.

This mod hides a few of its **own** settings by realm rank — that is why you are
not offered "True Immortal Max Qi" on a fresh character. The rank comes from
reading the realm name out of a setting's path. Applied to **another mod's**
config, that reasoning is simply wrong: a section named after a realm in
somebody else's namespace means whatever that mod says it means.

So a companion mod with a section called `mortal` had every setting under it
dropped — before a single row was built. The settings were in the file, backed
by live editable values, and claimed by the tab. The page came up empty with
nothing written to any log. From the outside it looked like the companion mod had
shipped a blank page.

A guard against this already existed and was asking the wrong question — it
tested whether a path was *qualified* rather than whether it belonged to
*another mod*, and an unqualified path is the only kind a custom tab can match in
the first place. Fixed, and now guarded against the exact fault.

## ❤️ Player Bars: a threshold, and no more double bars

**UI → Player Bars → Health** gains one setting: **Only Above This Much Health**.

Player Bars could already turn the heart row into a bar with the figure written
on it, in the hearts' own place, at the hearts' own width. What it could not do
was wait. It was on or off, for twenty health and for twenty thousand alike.

Twenty hearts is not the problem — two rows is readable, and you can see three
hearts missing without reading anything. The problem starts further up, where the
rows climb over the hotbar, over the chat, and over whatever you were looking at.

So set a number and the swap happens there:

```
onlyAboveMaxHealth = 40
```

40 is twenty hearts. Below it you get vanilla's own hearts, untouched; above it
you get the bar reading `12,480 / 18,000`. **0 means always, and that is the
default, so nothing about your HUD changes by installing this.**

It governs the hiding as well as the drawing, so there is never a frame with the
hearts gone and nothing in their place. Health only — hunger, armour and breath
are always twenty, so they have nothing to outgrow.

### 🤝 It stands down for other mods

Several mods replace the heart row, and two of them doing it on the same screen
means two bars drawn on top of each other in the same place. Neither mod is
wrong; they simply cannot see each other.

This one now asks the question of the frame rather than of a mod list: **has
anybody else already taken the hearts this frame?** If so, the health row stands
down and the rest of the HUD carries on. That needs no mod names, no version
checks and no agreement with anybody — it is right for whichever mod is doing it,
including ones that do not exist yet, and it stops being true the moment they
turn their own bar off.

The older bottom-left bar HUD stands down the same way when Player Bars are on,
so those two can no longer draw over each other either.

> **New installs only, on the defaults.** Player Bars now ships **on** for a
> fresh config, because icons are the wrong display for a mod where max health
> grows without limit. **If you already have a config file, your own setting is
> kept exactly as it is** — Forge only fills in keys that are missing. To take
> the new default, turn on **Enable Player Bars** under **UI → Player Bars**.

## 📌 On base mod updates

This mod hooks the base mod at runtime, so most of its updates need nothing from
this side — new content, retuned numbers and new items all carry straight
through. What does need an update here is a base-mod change that **moves or
renames something this mod reaches for**. This patch is a case in point, and it
is why the brittle hook above was replaced with a stable one.

If something this mod used to override stops working after a base mod update,
that is worth reporting with your `latest.log` — it is the fastest way to get it
pinned down.

**Checked against 0.1.1532:** all **599** injection points this mod uses resolve
in the new jar exactly as they do in the one it was made for — no class
renamed, no signature changed, nothing to repair. The server update is safe to
run with this mod.
